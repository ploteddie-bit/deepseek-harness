# Agent Note: 服务式工作区代码索引

Status: implemented

[English](2026-10-18-code-index-service.md) | 中文

## Problem

不了解代码库的 agent 会用 shell 工具搜索：每个标识符一次 `grep`，然后完整读取每个候选文件，换一个问题再来一次。在一个包含 6 356 个 TypeScript 与 JavaScript 文件的仓库上，这既慢又浪费上下文，而且不精确——按文本频次排序时，只是提到某个名字的文件会排在声明它的文件之前。agent 真正问的问题是「这个名字在哪里声明」，而 harness 现有能力都答不了：`ctx.sessionQuery` 索引的是会话记录，文件系统工具只能读取 agent 已知路径的文件。

2026-10-18 的 spike（`~/.dsh/docs/spike-code-index-20261018.html`）在任何编码之前就测量了各个选项。使用 `unicode61` 分词器的 FTS5 响应为 0,59 ms p95，但对 10 个完整标识符中只有 1 个把定义文件排在第一，5 个自然语言表达式只匹配到 1 个。同一语料上，使用 `trigram` 分词器的 FTS5 需要 13,11 s 与 236 MB，对 5 个自然语言表达式全部匹配，但 hit@1 仍是 0,10：BM25 会把提到名字的文件排在定义它的文件之前。仅符号表在 20–25 ms 内达到 hit@1 0,53。瓶颈是排序而非覆盖，修复方式必须把声明排在无关文本之前。

## Decision

[code-index 包](../../../../packages/context/code-index/README.zh.md)针对一个工作区提供服务 `ctx.codeIndex`。它把用于文件文本的 FTS5 trigram 表与由 TypeScript AST 提取填充的符号表结合起来，再与路径匹配融合为按路径的单一排序。不运行任何嵌入模型，服务也不持有向量存储。

### 服务接口与生命周期

`indexWorkspace({ force })` 遍历工作区、提取符号，并在单个事务中替换整个语料。它是唯一的写入方，且是显式的；在它运行之前 `search()` 不返回结果。`status()` 报告覆盖的工作区、是否已有一次完整运行记录了 `updatedAt`，以及文件数与符号数。`dispose()` 关闭数据库，之后每个调用都会显式失败。

工作区是 `process.cwd()`，在构造时捕获一次。它不是 Session 工作目录：该服务是进程级的，每个服务实例对应一个工作区，这与已启动的 harness 进程所服务的单一工作目录相符。`dbPath` 默认为 `:memory:`，因此索引由每个进程的第一次搜索重建；除非部署指定路径，否则不会在磁盘上留下可能过期的状态。

### 索引与排序

遍历收录 `maxFileBytes` 以内的 `.ts`、`.tsx`、`.js` 与 `.mjs` 文件，跳过符号链接与被排除的目录名，并在 `maxFiles` 处停止。声明来自 `ts.createSourceFile`，不是正则表达式：函数、方法、类、接口、类型别名、枚举，以及一条语句中的第一个具名变量。无法读取的目录会被跳过，因此一个权限错误不会让整次运行失败。

排序使用排序前就已确定的固定层级，因此结果可跨运行复现，而不是依赖语料的相对频率：精确声明名得 1,0，名称前缀 0,8，名称子串 0,6，路径子串 0,5，文本匹配 `0.4 / (1 + |bm25|)`，上限低于路径层级。同一路径保留最佳候选，结果按分数降序、再按路径排序，每个来源在合并前最多读取请求上限的四倍。少于三个字符的查询会跳过 trigram 检索，因为 trigram 索引无法服务它。

### 工具注册

插件在 `ctx.tools` 已经挂载时注册 `code_search`，并在 apply 时通过 `ctx.get('tools')` 读取该注册表。工具在首次调用时索引，因此挂载后无需单独的启动步骤；只需要服务的部署不会注册工具。

### 实测预算

在 6 356 个被索引文件上，spike 测得一次完整 trigram 运行 13,11 s，SQLite 文件 235,99 MB；文本查询 p50 4,04 ms、p95 8,25 ms，仅符号检索 p50 19,55 ms、p95 24,94 ms，173 593 个声明的符号提取耗时 0,93 s。保留的预算是每次运行低于 15 s、p95 低于 50 ms、体积低于 300 MB。每个实测数字都远低于 spike 设定的 300 ms 延迟预算，因此真正起约束作用的是索引体积与重建时间，而不是查询延迟。

## Alternatives considered

**在第一个版本就加入嵌入模型。** 本地没有可运行的嵌入模型，引入一个会带来模型下载、其内存开销，以及新的失败面，却要解决测量结果并未暴露的问题。实测差距在 hit@1 上，而符号表在结构上就能补上它。嵌入保持延期，只有在比本仓库更大的语料上融合召回仍低于 0,85 hit@10 时才重新评估。

**扩展 `ctx.sessionQuery` 以收录源文件。** `ctx.sessionQuery` 拥有会话记录及其保留策略与逻辑语料；源文件不是会话记录，也没有会话生命周期。把它们放进该存储会把代码索引绑到会话删除与会话查询面上，而且源文本的 trigram 表并不契合会话 schema。独立包配独立存储让两种生命周期互不牵连。

**再引入第三个搜索引擎。** 两个已测引擎已经干净地分开处理了两类场景：`unicode61` 是 0,59 ms p95 但对短语无效，trigram 是 8 ms p95 且能找到短语。第三个引擎——嵌入式库或外部服务——会增加一个依赖与一个部署面，却没有触及测量认定的那一层排序缺陷。把这份精力花在符号层级上不引入任何新依赖，就消除了文本引擎单独使用的理由。spike 预测融合排序的 hit@1 高于 0,60；该预测仍未验证，因为本包不附带任何检索评测，因此排序回归不会让任何 gate 失败。

## Consequences

每个进程的第一次搜索都要付一次完整工作区遍历：在这种规模的仓库上是 13 s 的同步工作，因为存储层使用 `node:sqlite` 的 `DatabaseSync`，且 AST 遍历是同步的。任何增量重建都被延期；配置 `dbPath` 会保留最后一次完整运行的语料，文件变化时不会自动重建。只有四种源码后缀被索引，因此多语言仓库只能部分覆盖；排序是词法的——没有 camelCase 拆分、词干还原或模糊匹配，因此 `workspaceChanges` 匹配不到 snake_case 查询。BM25 归一化相对于语料，这使分数在同一次索引运行内有意义，但跨运行不可比。
