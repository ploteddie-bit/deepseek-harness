# Agent Note: 编辑测试 guard

Status: implemented

[English](2026-09-06-edit-test-guard.md) | 中文

## 问题

模型可能长时间编辑文件却从不运行测试套件，累积了大量未经任何验证的改动。与循环卫生 guard 不同，没有任何提醒把“编辑”与“运行测试”关联起来。

## 决策

`dsh-edit-test-guard` 是一个建议性 guard：在编辑类或写入类工具调用之后，它会检查发起调用的 agent 是否在近期的工具调用窗口内运行过测试命令；如果没有，就投递一条简短提醒，要求运行相关测试。它从不阻止：编辑总是落地，工具结果不变，是否现在、稍后或永不测试仍由模型决定。

每个 agent 在 `WeakMap` 中保存最近 `window` 条序列化工具调用参数的有界历史。当调用名匹配 `editTools` 模式时，guard 扫描该 agent 的历史，查找是否有某条序列化参数包含任一 `testCommands` 片段（普通的大小写敏感子串匹配）。提醒随 post-execute 决策的 `additionalContexts` 传递并归属于插件；掉出窗口的测试运行会停止压制提醒。配置（`editTools`、`testCommands`、`window`、`reminder`、可选 `reminderText`）在 `apply` 中校验并在无效时抛出。

与循环卫生兄弟不同，此 guard 不随 `dsh` base 组合交付；组合在需要“编辑后测试”纪律时显式挂载它。

## 已考虑的替代方案

**阻止编辑直到运行测试。** 否决编辑会破坏合理的快速改动，并为每次文件触碰强制一次测试；建议性把决定留给模型。

**结构化跟踪测试命令。** 解析 shell 工具的 `command` 字段更精确，却把 guard 与工具形态耦合；对序列化参数做子串匹配刻意做得宽泛且可配置。

**共享循环卫生计数器。** 复用 repeat/failure 链状态会把“编辑未测试”与“失败循环”混为一谈；独立的 per-agent 窗口让信号互不干扰。

## 后果

- guard 仅建议且默认不启用；启用它是组合的选择。
- 对序列化参数的子串匹配可能把编辑名为 `test.js` 的文件误读为已运行测试；`testCommands` 是调优入口。
- 窗口驻留内存，因此恢复的会话以全新历史开始，恢复后立即编辑可能触发提醒。
